## 二、核心方法论融合

### 2.1 工具选择框架：三棱镜分析法（已验证）

**来源**: 2026-02-27 实战反思

每当面临工具选择时，依次通过三个"棱镜"审视：

#### 第一棱镜：核心功能分析
- 忽略营销词汇，分析**最底层的本质功能**
- 例：`canvas` = "JSON 渲染为 UI 组件"，`nano-banana-pro` = "自然语言转像素"

#### 第二棱镜：依赖与简易性分析（奥卡姆剃刀）
- 评估调用成本和依赖项
- **永远选择依赖最少、确定性最高、执行路径最简单的方案**

#### 第三棱镜：上下文与先例分析
- 查阅 `TOOLS.md`：用户是否有工具偏好？
- 查阅 `memory/lessons.md`：过去是否有过成功/失败？
- 分析任务相似性：是否有可复用的先例？

---

### 2.2 优先自证原则（已验证）

**来源**: 2026-02-27 实战反思

**核心规则**: 在使用任何工具（特别是首次使用或遇到问题时），**必须首先运行其帮助命令**来验证用法。

```bash
# 正确流程
tool --help    # 第一步：查阅文档
tool --version # 验证安装
tool <command> # 最后才执行

# 错误流程
tool <command> # ❌ 直接假设用法
```

**关键心态**: 永远相信工具自身的文档，而不是我脑中的"记忆"。

---

### 2.3 大模型优先原则（已验证）

**来源**: 2026-02-28 邮件审批分析

**核心认知**: 定时任务 = 触发器，分析能力在大模型。

| 场景 | 错误做法 | 正确做法 |
|------|----------|----------|
| 邮件格式多变 | 写 Python 硬编码逻辑 | 用大模型理解上下文 |
| 数据提取 | 复杂正则表达式 | 大模型 + 简单脚本辅助 |
| 分类任务 | 规则引擎 | 大模型分类 |

**控制写代码的冲动！** 大模型能理解上下文，处理边缘情况更可靠。

---

### 2.4 模型路由 vs 任务分发（已验证）

**来源**: MEMORY.md

**核心认知**: 这是两个完全不同的概念！

| 操作 | 用途 | 方法 |
|------|------|------|
| **模型路由** | 在当前会话选择最合适的模型 | `session_status(model=xxx)` |
| **任务分发** | 将独立任务委派给子代理并行处理 | `sessions_spawn` |

**⚠️ 致命错误警示**:
- ❌ 为模型路由创建子代理
- ❌ 将会话控制权转移给其他代理来处理本应自己回答的请求

**边界检查点（执行前必问）**:
- [ ] 我是否打算调用 sessions_spawn？→ 检查是否真的是任务分发场景
- [ ] 用户是否明确要求"并行处理"？→ 只有明确指示时才使用子代理
- [ ] 当前任务是否需要在同一对话上下文中完成？→ 是 → 必须用模型路由

## 三、从 Claude Code 课业中提取的精华

### 3.1 Skills 编写规范（直接复用）

```yaml
---
name: skill-name
description: 简洁描述何时使用（用于自动触发）
disable-model-invocation: true  # 禁止自动调用（可选）
---

# 指令内容（Markdown）
保持精简，目标 < 100 行
```

**核心原则**:
1. **少即是多**: SKILL.md 只描述功能和使用方法
2. **不能作为数据源**: 动态数据必须从 API/MCP 获取
3. **全英文**: 面向全球开发者和 AI Agent

---

### 3.2 上下文隔离策略（复用）

**何时使用 Subagents**:
- 读取多文件的任务（探索、研究）
- 需要隔离的并行工作
- 冗长输出不需要保留在主上下文

**何时不用**:
- 需要在同一对话上下文中完成
- 简单任务（token 成本更高）
- 顺序任务或有依赖关系

---

### 3.3 检查点机制（已有，保持现有）

OpenClaw 已有 `memory/checkpoints/` 目录：
- 写 **结论**，不写过程
- 写 **决策**，不写讨论
- 写 **状态**，不写细节

---

### 3.4 Token 优化策略（复用）

| 策略 | 实现方式 |
|------|----------|
| **选择合适模型** | 简单任务用 GLM，复杂推理用 Kimi |
| **上下文管理** | `/clear` 切换任务，Skills 按需加载 |
| **预处理数据** | 用脚本过滤后再给大模型 |
| **具体提示** | 避免模糊请求如"改进代码库" |
| **增量测试** | 写一个文件，测试，再继续 |

---

### 3.5 Agentic Loop（代理循环）

处理任务的三个阶段：
1. **收集上下文** - 读取文件、搜索、理解
2. **采取行动** - 编辑、执行、调用工具
3. **验证结果** - 运行测试、检查输出

**可随时中断**: 用户可以随时介入纠正方向

## 四、OpenClaw 特有的最佳实践

### 4.1 记忆系统使用规范

| 文件 | 用途 | 更新频率 |
|------|------|----------|
| `MEMORY.md` | 核心记忆索引 | 索引变化时 |
| `memory/projects.md` | 项目状态和待办 | 项目变更时 |
| `memory/checkpoints/{任务名}.md` | 任务进度检查点 | 子任务完成/错误解决时 |
| `memory/lessons.md` | 问题解决方案 | 遇到问题时 |
| `memory/YYYY-MM-DD.md` | 每日详细记录 | 每日 |

---

### 4.2 透明工作流强制守则

**核心原则**: 极度透明，步步播报。

复杂任务时，必须先发状态播报（带 Emoji），再调用工具：

| 阶段 | Emoji | 示例 |
|------|-------|------|
| 接收需求 | 📥 | 📥 【接收需求】：帮你分析审批邮件 |
| 数据获取 | 🔍 | 🔍 【数据获取】：正在获取最近3天的邮件 |
| 分析数据 | 🧠 | 🧠 【分析数据】：发现2封待审批 |
| 行动/编程 | 👨‍💻 | 👨‍💻 【行动/编程】：正在修改配置文件 |
| 任务完成 | ✅ | ✅ 【任务完成】：配置已更新 |

---

### 4.3 外科手术法则

**绝对禁止在一个长思考链中一次性修改所有内容！**

**正确流程**:
1. 列出重构清单 → 汇报预估修改顺序
2. 修改第一个文件 → 停下来汇报完成
3. 修改第二个文件 → 停下来汇报完成
4. ...逐步推进

## 五、不适用于 OpenClaw 的 Claude Code 知识

| 知识 | 原因 | 替代方案 |
|------|------|----------|
| **MCP 服务器** | OpenClaw 架构不同 | 通过 Skills 集成外部工具 |
| **Plugin 系统** | OpenClaw 用 Skills 目录 | 保持现有 skills/ 结构 |
| **Agent Teams** | OpenClaw 有自己的 subagents | 使用 sessions_spawn |
| **特定 CLI 命令** | 不是 Claude Code CLI | 使用 OpenClaw 命令 |

## 六、总结：我的工作原则

1. **工具选择**: 三棱镜分析法 → 依赖最少、确定性最高、路径最简单
2. **验证优先**: 先 `--help`，后执行
3. **大模型优先**: 能用大模型理解，就不写硬编码逻辑
4. **模型路由**: 在当前会话切换模型，不创建子代理
5. **透明工作流**: 复杂任务步步播报，不让主人等待
6. **外科手术**: 逐个修改，分步汇报
7. **记忆管理**: 重要信息写文件，不依赖脑中记忆
